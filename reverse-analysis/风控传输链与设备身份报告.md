# 风控传输链与设备身份报告

> 上游索引：[风控研究总览](风控研究总览.md)。本报告覆盖安全数据 blob 如何转化为设备身份（nuid）、经哪些 HTTP 通道上行，以及 NetHT 自身的加载条件与调用者。
> 证据等级沿用总览定义。抓包相关结论来自既有 HTTP Toolkit 捕获（`CAPTURE_ENVIRONMENT=PROXIED`，长度/结构差分可复现，不构成无扰动环境声明）。

## 1. 传输链总图

```text
酷安启动
   ↓
Shuzilm 数链魔方 init（cn.shuzilm.core.Main.init，RSA 公钥）
   → DID（'D' 前缀）持久化 pref
   ↓
NetEaseProtectSDKManager.initializeDeviceIDInternal（协程回调）
   ↓
HTProtect.getToken（businessId, path）
   主线程校验 → FutureTask + Thread + 超时
   ↓
WatchMan$DynamicTask.call → JNIFactory.aebd1811194e82d9（businessId）
   ↓
native 0x243B18：gate（初始化总门 / 空参）→ 记录 "gt"
   → 0x213814 构建 blob（eventType 6 = 事件队列 + installedApk field 12）
        ├─ status 200（4B status + blob）
        │    → AntiCheatResult → nuid
        │      （AtomicReference 进程内持有，日志 "nuid loaded"）
        └─ 失败回退：ioctl(301, businessId) / ioctl("302|"+code)
   ↓
X-App-Device 复合头组装：DID + nuid + 机型串
   → UTF-8 → Base64 → StringBuilder.reverse() → 去换行 / 补位
   → CoolMarketHeaderInterceptor 逐对写头，随每个 API 请求常驻

平行通道（不经过上面的 nuid 主链）：
   ├─ getToken 白名单路径（init / indexV8 / checkLoginInfo）
   │    → _v2_post_token（仅 createFeed / reply 的 POST 表单）
   └─ Shuzilm getSessionSync（useDDISessionId 门控）
        → ddid Cookie（含 TTL）
另：X-App-Token = AuthUtils.getToken（由 X-App-Device 值派生，E2）
```

## 2. X-App-Device 复合头（E3 全链）

### 2.1 组装结构

复合串构造序（头对数组构造函数，酷安全部 API 头在此构造）：

```text
复合串 = [MainInit.useDDI 门控首字段：Shuzilm DID + nuid（剔除 '[-_0]' 字符）]
       + "; ; ; ; " + Build.MANUFACTURER
       + "; " + BRAND + MODEL + DISPLAY
       + OAID 管理器值 + …
→ getBytes(UTF-8) → Base64.encodeToString → StringBuilder.reverse()
→ Regex("\r\n|\r|\n|=") 替换为空（去换行去补位）
→ ("X-App-Device", value) 请求头对
→ HttpClientFactory$CoolMarketHeaderInterceptor.intercept 逐对写入
```

抓包观测的"DDI 开启后末尾新增固定 64 字符字段"与该结构精确吻合：value 是**反转后**的串，复合串首字段（DID + nuid）反转后位于末尾。

### 2.2 抓包差分证据（同启动周期，可复现）

- `/v6/main/init` 请求的 `X-App-Device` 为 132 字符，按宿主编码逆运算（reverse → Base64 decode）得 99 字节基础设备记录；
- 该响应下发 `useDDI=1` / `useDDISessionId=1` 后约 0.3–0.5 秒，`/v6/main/indexV8` 与 `/v6/account/checkLoginInfo` 均使用完全相同的 212 字符扩展头；解码后同一基础结构，末尾新增分号分隔的 64 字符字段（= 反转后的首字段）；
- 解码后的基础记录形如 `DU6F…k06; ; ; ; <厂商>; <品牌+机型>; <机型版本>; …`（首字段 'D' 前缀 = Shuzilm DID，实测吻合；设备标识已脱敏）；
- `/v6/main/init` 自身在取得开关前只发基础版本；同期请求无独立 DDI query/body 参数。

### 2.3 历史检索阴性的根因（方法学教训）

wrapper 长期搜不到的原因有三：

1. **头名实为 `X-App-Device`（首字母大写）**——此前全部 dex/内存/APK 检索用小写 `x-app-device` 做大小写敏感匹配，必然漏检（`X-App-Token`/`X-App-Id` 等同理）；
2. wrapper 不在盘上 APK：base APK 的 classes.dex 为易盾壳，仅含 30 个 `com.netease.nis.wrapper.*` 壳类，真实代码运行时解密；
3. 9.67MB 的"业务 DEX"不含网络层（okhttp 有、全部酷安 API 头常量无）——网络层位于另一个运行时 DEX。

## 3. nuid 生命周期

| 问题 | 结论 | 等级 |
|---|---|---|
| 生成方式 | 启动期 `getToken(businessId)` → aebd blob（= 事件队列 + installedApk field 12）→ nuid | E3 |
| businessId 来源 | 远程配置 `PostToken.businessId`（`/v6/main/init` 下发的固定值，形如 `aca7df…68e9`，已脱敏） | E3 |
| 失败回退 | FutureTask 超时 → `ioctl(301, businessId)` / `ioctl("302|"+code)` | E3 |
| 持有方式 | AtomicReference 进程内持有；可读存储未发现持久化短路；DB 受 SELinux 保护不可读 → 持久化 UNKNOWN | E2 |
| 刷新触发 | Shuzilm initID 完成、onLoginEvent / onWifiEvent（ShuzilmSDKManager 观察者）、RequestSessionIDUpdater 对 init / indexV8 / checkLoginInfo 的白名单触发 | E3 |
| 与 field 12 的关系 | 每次 getToken 都走 blob builder；field 12 只在缓存有未上报记录时有内容（默认严格增量，见采集报告） | E3 |
| **在场条件（重要修正）** | **NetHT 懒加载**：仅 NetHT 已加载的会话才有 nuid / DDI 扩展头；未加载会话只有基础 X-App-Device（见 §5） | E3 |

## 4. 平行传输通道

| 通道 | 触发与门控 | 载体 | 内容 |
|---|---|---|---|
| `_v2_post_token` | `RequestSessionIDUpdater` 白名单（/v6/main/init、/v6/main/indexV8、/v6/account/checkLoginInfo）+ 远程配置 `PostToken.businessId` / `PostToken.List=[createFeed, reply]` | 仅 `*.coolapk.com` 的 POST：FormBody 追加表单字段 | 每次 getToken 管道产出的 token（与 nuid 共用 `HTProtect.getToken → aebd` 管道，语义独立） |
| `ddid` Cookie | `RequestSessionIDUpdater` / 登录 Cookie 助手；`MainInit.useDDISessionId` 门控（当前 =1） | Cookie（含过期检查与 TTL） | Shuzilm `getSessionSync` 会话标识 |
| `X-App-Token` | 每请求 | 请求头 | `AuthUtils.getToken(context, X-App-Device 值)` 派生；AuthUtils 定义不在已恢复的 4 个 dex 中（native 或未恢复 dex，E2） |

DDI event 白名单（`MainInit.useDDIEventList`）当前为 createFeed / reply / like / likeReply / message / send；`MainInit.useDDIEvent` 当前为 0（事件通道关闭）。

## 5. NetHT 的加载条件（懒加载，根因模型关键修正）

### 5.1 懒加载实测（E3）

观测会话：冷启动 → 主页 → 反复滑动 feed + 帖子详情 + 评论区，持续约 10 分钟：

- 进程 maps 中 **libNetHTProtect.so 从未出现**（对照 APK 内偏移区间无任何映射）；
- logcat 无任何 `nuid` / `htprotect` / `netht` / `shuzilm` 痕迹；
- UI 正常渲染、壳（nesec）正常工作；Pangle/live.lite 组件映射同样为 0（同为懒加载）。

推论：
1. "每次冷启动 NetHT 初始化 + nuid 常驻上行"不成立；仅 NetHT 已加载的进程，其请求头才可能携带 nuid/DDI 复合值。
2. NetHT 全部信号路径（installedApk field 12、周期扫描器、事件队列）**只存在于 NetHT 已加载的会话**。
3. 与早期观察"DDI 开关后 x-app-device 出现 64 字符扩展字段"拼合：开关性质，当前会话该门为关。

### 5.2 触发条件研究（E3 排除 + 边界）

| 假设 | 结论 |
|---|---|
| 登录态触发 | **排除**：设备实际已登录（UI 实证，账号 ID 已脱敏），登录态真实浏览后 NetHT 仍零加载 |
| 加载门性质 | 业务侧配置门（服务端配置键或特定业务流程），当前会话为关 |
| 触发门具体键 | UNKNOWN（需门开时的会话样本或对运行时 DEX 完整反编译） |

### 5.3 调用者闭合（E3）

对运行时 DEX（nesec 解密后内存 DEX）的迷你解析器分析：

- **调用者类 = `com.coolapk.market.manager.NetEaseProtectSDKManager`**（真实业务类名；类簇含协程链 initializeDeviceIDInternal / onRealInit 等，以及 OaidManager 的 OAID 证书下载逻辑）；
- **并行独立 SDK：数链魔方 `cn.shuzilm.core`**（Main / Listener / BuildConfig）+ 宿主 `ShuzilmSDKManager`（getSessionSync / initID / postEventAndGetSessionID）——X-App-Device 链中 "SHUZILM" 字样的归属就此闭合；
- HTProtect 封装类持有：**productId = "YD00000551137681"**（易盾产品号）、配置键 **"PostToken.productId"**；
- 该业务管理器不在静态壳 dex 与已恢复业务 dex 中（两者 htprotect 引用均为 0），全部位于运行时 DEX——与加壳模型一致。

## 6. 运行时 DEX 与加壳背景

- 盘上 base APK 的 classes.dex（约 101.6MB）为易盾壳：仅 30 个 `com.netease.nis.wrapper.*` 类，真实业务/安全代码运行时解密；
- 已恢复的关键运行时 DEX：业务 DEX（约 9.67MB，11,278 类，头部 4 字节曾损坏已修复并通过 Adler32/SHA-1 校验）、网络层 DEX（含全部 API 头构造与 X-App-Device 组装）、NetHT wrapper DEX（HTProtect / WatchMan / JNIFactory Java 侧）；
- 加壳器（libnesec.so）本体分析见[跨版本差分与外围组件报告](风控跨版本差分与外围组件报告.md)。

## 7. 传输层小结

1. **持久上行的只有基础设备身份**：Shuzilm DID + 机型串组成的 X-App-Device 基础值随每个 API 请求发送（与风控决策的相关性取决于服务端）。
2. **nuid 是条件性的**：仅 NetHT 已加载的会话在场；其内容（事件队列 + field 12）在探针门全 OFF + 包通道权限关闭的本机上高度收敛。
3. 每请求独立的安全 token 是 `_v2_post_token`（仅发帖/回复），与 nuid 共用 getToken 管道但语义独立。
4. metasec 有完全独立的上行与签名通道（见[跨版本差分与外围组件报告](风控跨版本差分与外围组件报告.md) §6），不经过 NetHT 管道。
