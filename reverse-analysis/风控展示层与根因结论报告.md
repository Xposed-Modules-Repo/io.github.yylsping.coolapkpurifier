# 风控展示层与根因结论报告

> 上游索引：[风控研究总览](风控研究总览.md)。本报告覆盖"风险提示行从哪里来"的展示层分析与最终根因结论、模块影响评估。
> 证据等级沿用总览定义。

## 1. 问题定义

风控问题的最终可见形态是信息流中疑似"风险提示行"。在无风险阳性样本（原始 Feed 响应 + 同时间 UI 证据）的条件下，需要回答：客户端是否存在该行的生成代码，还是服务端驱动的展示。研究把可能模型收敛为四类：

```text
S1：普通 card + text 即可（零模板约束）
S2：需要已有通用 template ID，但不需要 risk 专用客户端代码
C1：客户端必须收到某 flag 后主动构建
UNKNOWN：证据不足
```

## 2. 已排除的客户端硬编码模型

对恢复的业务 DEX（11,278 类）、APK 解包资源和可用运行时 DEX 的定向搜索（E3 阴性）：

- 无风险文案、`risk`/风控 flag、风险专用 `entityTemplate`，无带这些常量的 Feed item builder；
- 无任何针对模块的硬编码特征字符串（模块包名、模块文件名前缀、libdexkit、XposedBridge/LSPosed/Zygisk/Magisk/Riru/Edxp、/proc/self/maps、DexPathList 等精确搜索全部 0 命中）——降低 Java 侧"按固定字符串直查"概率，但不排除 native、远程下发或通用枚举匹配；
- 12 份成功的 `/v6/main/indexV8` 响应完整分页解压检查：只出现普通 `card` / `feed` / `feed_reply` / `iconLink` / `imageText` / `product` / `topic` / `user` 等 entityType，无风险专用 entity/template（该阴性批次只证明"捕获窗口内无风险行"，不构成反证）；
- Kwad（快手广告 SDK）存在环境标志模型（`isRoot, isXPosed, isFrameworkHooked, isVirtual, isAdbEnabled, isEmulator, isGroupControl` 的序列化能力），但构造器/setter/toJson 无外部直接 xref——只能定性为"SDK 内存在该能力"，不能写成"酷安已经上报 Xposed"；其安装列表获取路径仅在宿主提供自定义 controller 时调用，恢复 DEX 中无宿主实现。

## 3. 通用 server-driven card 模型（结论：S2）

### 3.1 分发结构（E3 静态）

```text
服务端 JSON row → Entity（getEntityType()/getEntityTemplate()/getTitle()/getUrl()…）
→ 各 Fragment/ViewHolder 对 entityTemplate 做显式 when-chain 匹配（无全局反射注册表）
→ 命中模板的 ViewHolder 用 DataBinding 渲染
```

关键实证：

- **通用 `card` 模板**（EntityCard → 专用 ViewHolder）：`getTitle()` → 标题 TextView（**任意服务端文本**）；`getUrl()` → "see_more" 跳转行；`getEntities()` → 嵌套 RecyclerView 子列表（实体可递归下发）；JSON 中 `cardContainerPadding*` 等键 → **服务端直接控制卡片样式**（无需客户端发版）。
- **configCard**：`DataListFragment` 对 `entityTemplate=="configCard"` 的实体经 JSON 转换直接应用为页面配置——服务端可通过任意列表响应注入配置卡片，客户端零专用代码即消费。
- **textCard 模板族**：`textCard` / `textCarouselCard` / `textLinkCard` / `textLinkListCard` 在模型/网络层 DEX 字符串池确认存在（渲染字段结构与 card 同构）。
- 模板名常量池还含 `pageTitle`、`headCard`、`iconScrollCard`、`sortSelectCard`、`hotSearch`、`searchHotListCard` 等通用文本承载模板。
- 调试基建佐证统一渲染框架：`CoolapkCardView` 内建 `show_card_info` 调试浮层，显示 `ViewHolderSimpleName => entityType -> entityTemplate`——**(entityType, entityTemplate) 就是渲染分发的全部键**。
- 正常样本验证：通用 `card` 模板在真实 Feed 流中使用；`/v6/main/init` 响应含 textCard/configCard 样本。

### 3.2 判定

1. 存在多个通用文本承载模板，服务端可下发任意文本 + 任意嵌套实体 + 服务端样式 → 满足 S2；
2. 分发键只有 (entityType, entityTemplate)，无第三类客户端 flag → 不满足 C1；
3. 不是 S1：文本不能脱离模板体系渲染，必须命中已知模板名；
4. 客户端无风险专用文案/template/builder（§2 阴性）。

**含义：若风险提示行真实存在，其最低成本实现是服务端在任意列表响应中插入 `card`/`textCard`/`pageTitle` 行，复用通用渲染，客户端零配合代码。**

## 4. 专用警示资产（展示能力强化）

16.6.1 运行时 DEX + 业务 DEX 中确认存在专用警示渲染资产：

| 资产 | 内容 | 等级 |
|---|---|---|
| `layout/feed_warning_0` + `FeedWarningBinding(Impl)` | DataBinding 生成物 + tag 校验串（实际使用的布局族） | E3 |
| `layout/item_alert_message_card_0` + `ItemAlertMessageCardBinding(Impl)` + `AlertMessageCardViewHolder`（源文件 `AlertMessageCardViewHolder.kt`） | 持警示配色常量（红 `#19DB4437` / 粉 `#FDD9D7`）的通用消息警示卡 ViewHolder | E3 |
| `MessageCard`（AutoValue 模型）+ `MessageCardDialogFragment` | Entity+Contacts 驱动的弹窗——**Entity→Dialog 通路存在**（当前样本用于"分享成功/去私信"） | E3 |

边界：`AlertMessageCardViewHolder` 的实例化点未找到直接 xref（仅自身 `<clinit>`），推测经工厂/反射注册或位于未恢复 dex 区（E2）；其宿主页面（消息中心 vs 主 feed）未定。

## 5. 网络中间件核查与假阳性排除

- okhttp 链上的 Interceptor 均为请求侧（头/Cookie/POST 字段/动态域名/图片 Referer 等），**未发现改写响应、注入列表行的 response middleware**；
- 字符串含 "Interceptor" 的 `NodeFeedDialogInterceptor` / `FeedReplyTopDialogInterceptor` / `FeedReplyRecommendDialogInterceptor` 实为 UI 层置顶/弹窗修饰器——假阳性已排除（E3）；
- `ipRiskRating` 等字样经上下文核验属腾讯网络组件（ipSpeedTask/ipneigh 等），与安全流无关——假阳性已排除（E2）。

## 6. 展示层结论

```text
PRESENTATION_CAPABILITY = high confidence
  （S2 通用 card/textCard + 专用警示卡资产 + Entity→Dialog 实证通路）
ACTUAL_RISK_ROW_ENDPOINT = UNKNOWN
  （无风险阳性样本，结构性无法收敛）
LIKELY_CARRIER（候选，按可注入性排序）：
  a. 任意列表响应中的通用 card/textCard 行（零客户端配合）
  b. 消息/通知列表的 alertMessageCard 行（专用资产已就位）
  c. Entity 驱动 Dialog（MessageCardDialogFragment 通路）
```

## 8. 模块影响评估

### 8.1 五项"触发模块改动"的判据（M1–M5）核对结果

| 判据 | 结果 |
|---|---|
| M1：当前仍存在的 Hook 被安全 collector 明确观察 | 不成立——唯一可能"看见"Hook 环境的 NetHT 探针面门恒 OFF 且不可翻转；metasec 的 JNI vtable 完整性探针检测的是 JNI 函数序言 inline-patch，模块的 Java 层 hook 不改写 JNI vtable 函数本体 |
| M2：模块特征文件被直接写入 security payload | 不成立——field 12 元素仅含包名+权限标注+label；宿主私有目录枚举不存在，模块文件无采集边（E3 阴性） |
| M3：某个净化行为直接进入安全校验 | 不成立——未发现任何净化行为到安全逻辑的消费边 |
| M4：Reply 临时 ClassLoader Hook 与检测窗口存在直接边 | 不成立——临时 Hook 已在 READY 后退休，无直接消费边 |
| M5：Feed 删除行为被安全逻辑直接消费 / collector 对模块包名专属匹配 | 不成立——collector 把模块包当普通第三方包处理，无包名专属匹配；本机 OS 权限门之下模块包名根本不进入采集 |

### 8.2 模块行为的风险面分析（研究过程中的背景结论）

- **Feed after-filter**：先完整执行宿主方法，再对返回 List 过滤；不修改 response/cursor/page，不伪造曝光成功回调。宿主曝光结束链按已收集的可见项工作，被删广告自然不进入下游曝光队列——该机制早于 2.2.0，且未发现与安全风控的直接边。
- **Splash decision（shouldShowAd）**：完整字节码反证该函数只有读取和判断、无关键写副作用；"PRE_BLOCK 跳过关键状态写入"假设被推翻。Mode A 起彻底不 Hook 该方法。
- **2.2.0 曾有的新增 framework Hook 面**（5 个 Settings Hook + 2 个 layout/tag fallback）：曾是最强的版本差分型模块风险路径候选，已在 Mode A 全部移除；后续 Mode A-ZF 实现正常 READY 后零 framework Hook（HookLedger 记录证实），临时 discovery Hook 在终态完全退休。
- **模块包可见性**：模块是普通第三方包（约 1.1MB），无大小豁免问题；在权限授予的 ROM 上理论上进入 installedApk 采集（每包每进程一次），本机则被 OS 权限门完全挡住。

### 8.3 工程决策

```text
KEEP MODE A-ZF FROZEN / NO MODULE PATCH
```

依据：M1–M5 全部不成立；"靠删 Hook 降低检测面"在探针门不可翻转、NetHT 懒加载的结论下失去对象——最活跃的检测面（metasec）检测的是环境与行为基线（root/Magisk 路径、adbd、自动化应用、本地端口、IP），与模块增删无关。

## 9. 证据边界

无风险阳性样本条件下，以下事项结构性不可闭合（诚实边界，非待办）：服务端打分逻辑与风险行下发条件、实际风险行 endpoint、警示卡的具体分发 template、metasec 上报的具体 host。完整清单见[总览](风控研究总览.md) §8。
