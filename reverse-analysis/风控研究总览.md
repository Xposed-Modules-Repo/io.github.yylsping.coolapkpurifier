# 酷安风控问题研究总览

> 本报告是风控逆向研究的主索引与总报告。整套研究回答一个核心问题：
> **酷安客户端把哪些环境/设备/应用信号采集并上行到服务端，服务端风险状态又以什么形态回流到客户端界面。**
>
> 研究背景：在运行去广告模块（酷安净化）且处于 Xposed 环境的设备上，酷安信息流中出现疑似"风险提示行"，怀疑与模块或 Hook 环境相关。研究全程**未制造风险阳性、未修改冻结的模块、未绕过任何保护机制**，仅通过静态逆向、只读运行时观测与既有抓包推进证据链。

## 1. 研究方法论

### 1.1 证据等级

| 等级 | 含义 |
|---|---|
| **E3** | 指令级 / 字节级 / 数据流级 / 实测传输直接证据（反汇编、重建解码字符串、抓包差分、设备实测时间戳） |
| **E2** | 强结构推断（全密钥集群扫描、字符串池时间线、接口调用侧证据） |
| **E1** | 弱支持性证据 |
| **UNKNOWN** | 证据不足，明确保留，不用推测填充 |

### 1.2 推理红线

研究全程强制区分以下五层，任何一层都不允许越级声明为下一层成立：

```text
客户端具备能力 ≠ 运行时已激活
运行时已激活   ≠ 已进入传输通道
已进入传输通道 ≠ 服务端实际采用
服务端可展示警示 ≠ 实际风险行 endpoint 已确认
```

- 单次阴性不排除路径，单次阳性不直接归因；不以"未复现"推断"风险已消失"。
- 不为取得风险阳性制造高风险条件（不申请额外权限、不改 ROM/AppOps、不隐藏 LSPosed、不伪造包列表、不篡改 nuid/X-App-Device、不阻断安全上报端点）。
- 抓包/代理环境视为可能扰动目标行为的实验条件，相关结论须标记 `CAPTURE_ENVIRONMENT=PROXIED`。
- 研究轮不修改模块源码与 Hook 面；模块处于冻结状态。
- 反篡改观测：对酷安进程 `/proc/<pid>/mem` 的连续读取会触发易盾反篡改升级（先零填充返回、后连同 maps 一并拒绝）；研究全程未对抗、未绕过，仅采用只读 maps / 文件时间戳等安全观测手段。

### 1.3 研究对象与环境

| 项 | 值 |
|---|---|
| 目标应用 | 酷安（com.coolapk.market），主要研究版本 16.6.1（2608212），历史对照 16.5.1 / 15.9.0 |
| 保护壳 | 网易易盾（libnesec.so 自解壳 + 运行时解密 DEX） |
| 安全组件 | NetHT（libNetHTProtect.so 5.7.6，易盾 HTProtect）、metasec（libmetasec_ml.so，字节/Pangle 广告供应链）、数链魔方（cn.shuzilm.core） |
| 模块 | 酷安净化 2.2.0 / 2.2.1（冻结观察状态） |
| 实测设备 | root + LSPosed 环境，Android 16 / ColorOS；应用列表运行时权限 `GET_INSTALLED_APPS` 处于拒绝状态 |

## 2. 整套风控流程示意图

当前证据链下的完整风控流程如下（关键处标注证据等级；纯文本绘制，保证任意渲染环境字号一致可读；详细分析见分报告）：

```text
总干道：① 客户端采集 ──→ ② 身份构建 ──→ ③ 传输层 ──→ ④ 服务端风控黑盒 ──→ ⑤ 服务端驱动展示
旁路  ：metasec（①B）───────────────────────────→ ④（x-bdms 上行 / 广告请求签名，不经 ②③）


═══════ 第①层 客户端采集（三套并行组件，全部懒加载 / 条件加载） ═══════

  A. NetHT（网易易盾 HTProtect 5.7.6；调用者 NetEaseProtectSDKManager；
     业务配置门控加载，触发键 UNKNOWN）
     ├─ installedApk 采集器
     │    pm list packages -f --show-versioncode -U -3（仅第三方包）
     │    → 内存缓存 → enrich（≤200MiB 大小门 + 敏感权限标注）
     │    → field 12 元素 = 包名 + 权限标注 + label（每包每进程至多一次）
     ├─ 注入/环境探针：LSPosed maps / Zygisk ptrace / odex inline-max /
     │    smaps / fdinfo-mnt
     │    ※ 门构造默认全 OFF，库内无运行时写入者 → 结构性静默（E3）
     ├─ 周期扫描器：1min 扫描电池 / 30min 大清扫 / 10min 包缓存刷新
     │    black_module 非常规路径 APK 检测等，命中即推事件
     └─ 并行采集面：filePermisson / mis / uid_match / changedPackages
          ※ 默认 OFF

  B. metasec（字节 / Pangle 广告供应链；本机 08-26 10:43 首次激活）
     root / Magisk / 自动化应用 / IP 采集
     + JNI vtable inline-hook 完整性探针 + 本地端口 / HTTP 探测

  C. Shuzilm 数链魔方 SDK（'D' 前缀 DID 设备标识，持久化）

  ※ 关键约束（实测设备）：OS 权限门 GET_INSTALLED_APPS = denied
     → NetHT 的 pm 采集以应用 UID 执行，只能看到宿主自己
     → 本机 installedApk 通道不含任何第三方包（含模块）

        │  A 的事件队列 + installedApk field 12
        ▼

═══════ 第②层 身份构建（仅 NetHT 已加载的会话发生） ═══════

  aebd1811194e82d9（getToken，eventType 6）
  security blob = 全局安全事件队列 + installedApk field 12
        ↓
  nuid（启动期一次性生成，进程内持有；失败回退 ioctl 301/302）

        │  nuid
        ▼

═══════ 第③层 传输层（五条并行通道） ═══════

  ├─ X-App-Device 复合头 ← C 的 DID + ② 的 nuid + 机型串
  │    reverse + Base64；随每个 API 请求常驻上行
  ├─ _v2_post_token：仅发帖 / 回复（createFeed / reply）的 POST 表单
  ├─ ddid Cookie：init / indexV8 / checkLoginInfo
  ├─ X-App-Token：由 X-App-Device 派生（E2）
  └─ B 的独立通道（不经 ②③）：
       x-bdms-payload → TTNet 上报 mssdk 后端（aid 219989）
       + getFeatureHash 签名进每一个 Pangle 广告请求

        │
        ▼

═══════ 第④层 服务端风控黑盒 ═══════

  打分 / 阈值 / 策略不可见
  16.5.1 → 16.6.1 客户端安全栈零差分（E3）→ 服务端策略解释力最高
        ↓  风险状态以服务端驱动形式回流

═══════ 第⑤层 服务端驱动展示层 ═══════

  通用 card / textCard 模板（零客户端配合即可渲染任意服务端文本）
  专用警示资产：feed_warning 布局族 / AlertMessageCardViewHolder（红粉配色）
  Entity→Dialog 通路（MessageCardDialogFragment）
  ※ 实际风险行下发 endpoint UNKNOWN（无阳性样本，结构性不可闭合）
```

## 3. 流程文字简述

**采集层（客户端）。** 酷安的安全信号采集由三套并行组件承担，全部为懒加载/条件加载：

1. **NetHT（易盾 HTProtect）**：由宿主业务类 `NetEaseProtectSDKManager` 触发加载（加载门是业务侧配置，具体键 UNKNOWN）。它内部有四类采集面——
   - **installedApk 采集器**：以应用自身 UID 执行 `pm list packages -f --show-versioncode -U -3` 枚举第三方包，入内存缓存并做大小门/敏感权限标注富集，序列化为 protobuf field 12 的字符串元素（`marker + {MD5} + 包名+标注+label`）。默认**严格增量**：每个包在进程生命周期内至多上报一次；"gt 全量快照"模式因配置门恒 0 且库内无写入者而**结构性不可能激活**。
   - **注入/环境探针**（LSPosed 内存特征、Zygisk ptrace、ART 编译参数、smaps、framework JAR 挂载等）：配置门在构造时一次写入为默认全 OFF，全库不存在任何运行时写入者（含配置应用通路白名单核对）——这些探针在该构建中**结构性静默**。
   - **周期扫描器电池**（1 分钟 / 30 分钟 / 10 分钟）：含针对非常规路径 APK 的 `black_module` 检测等，命中即向全局安全事件队列推事件并可立即触发安全数据构建；输入由"命令批"数据驱动（Java ioctl 注入 / 伪装资源文件 / 跨注册表传播），实测设备上伪装资源文件不存在。
   - **并行采集面**（外存 Android/data 目录权限位扫描、相邻 UID 扫描、共享 UID 异名、卸载/变更检测）：默认关闭。
   - 宿主私有目录枚举在 NetHT 中**不存在**；模块私有文件无任何采集边（E3 阴性）。
   - OS 权限门：实测设备 `GET_INSTALLED_APPS` 被拒，`pm list -3` 以应用 UID 执行时只能看到宿主自己 → **本机 installedApk 通道实际不含任何第三方包（含模块）**。
2. **metasec（字节/Pangle 广告供应链）**：随直播组件动态下发，本机 2026-08-26 10:43 首次激活（与风控观察窗口同日）。采集 root/Magisk 路径、自动化应用、本机 IP、JNI vtable inline-hook 完整性、本地端口/HTTP 服务等环境信号，结果经三条路输出：`report("cold_start")` 事件 → `x-bdms-payload` 头 → TTNet 上报 mssdk 后端；`getFeatureHash` 签名进**每一个 Pangle 广告请求**；本地 `.msdata/mssdk/ml` 风险库。
3. **数链魔方（Shuzilm）**：生成 'D' 前缀的持久化 DID，作为设备身份的一部分。

**身份构建层。** 当 NetHT 已加载时，`JNIFactory.aebd1811194e82d9`（getToken）在启动期一次性构建 security blob（= 事件队列 + installedApk field 12），产物 nuid 进程内持有。NetHT 未加载的会话没有 nuid——实测正常登录态浏览会话 NetHT 全程不加载。

**传输层。** nuid 与 Shuzilm DID、机型串组成复合串，经 Base64 + 反转后写入 **X-App-Device** 请求头，随每个 API 请求常驻上行；`_v2_post_token`（仅发帖/回复 POST）、`ddid` Cookie、`X-App-Token`（由 X-App-Device 派生，E2）构成平行通道。metasec 走独立的字节系上报链与广告请求签名链。

**服务端黑盒。** 打分/阈值/策略完全不可见；跨版本差分证明 16.5.1 → 16.6.1 客户端安全栈逐字节零变化，时间相关性的解释力集中于服务端策略与外部供应链（Pangle 组件独立时间线）。

**展示层。** 客户端具备充分的服务端驱动展示能力：通用 `card`/`textCard` 模板可渲染任意服务端文本（零客户端配合），另有专用警示资产（`feed_warning` 布局族、红/粉配色的 `AlertMessageCardViewHolder`、Entity→Dialog 弹窗通路）。实际风险行的下发 endpoint 在无阳性样本条件下无法收敛，标为 UNKNOWN。

## 5. 最终根因排序

综合全部证据后的风险归因排序（第 1、2 位并列主导且互不排斥——metasec 采集 → 服务端打分 → 展示本就是同一条链的两段）：

| # | 假设 | 状态与依据 |
|---|---|---|
| 1 | **metasec（Pangle 供应链）独立信号 + 服务端消费** | 唯一同时满足"检测能力 E3 + 本机实测激活 + 激活时刻（08-26 10:43）与观察窗口（08-25/26）重合"的检测面；上行通道已闭合（x-bdms-payload → TTNet mssdk 后端；getFeatureHash 进每个广告请求）；剩余缺口仅"服务端是否将其用于本次风险决策"（无阳性样本，结构性不可闭合） |
| 2 | **服务端 policy / 阈值 / rollout**（对既有信号打分：基础设备头、X-App-Token、行为序列） | 16.5.1 → 16.6.1 客户端安全栈零差分（E3）+ NetHT 探针通道结构性静默（E3）→ 客户端版本间解释力≈0；展示层能力充分（E2/E3） |
| 3 | **NetHT 周期扫描器事件**（black_module 等） | 能力 E3、默认每分钟运行；但输入由命令批数据驱动，本机伪装资源文件不存在，Java ioctl 注入是否存在取决于酷安业务侧（UNKNOWN）；且仅 NetHT 已加载的会话在场 |
| 4 | ROM / 权限差异路径（其它设备上应用列表全量上传） | 本机该通道被 OS 权限门关闭（E2 实测）；在授权 ROM 上该能力自 16.5.x 起存在且每次冷启动事实上全量上报，条件性成立 |
| 5 | ~~服务端远程翻转 NetHT 探针门~~ / ~~LSPosed·Zygisk 信号经 NetHT 上行~~ | **已排除（E3）**：探针门构造时一次写入、库内无任何运行时写入者、配置应用通路白名单不含门；且多数会话 NetHT 根本不加载 |
| 6 | 模块特有行为 | 无证据：模块包被采集器当作普通第三方包（无包名专属匹配）；field 12 不含 Hook/文件特征；本机 OS 权限门之下模块包名根本不进入采集；未发现任何"当前模块行为 → 活跃安全采集"直接边 |

模块侧工程决策：**Mode A-ZF 冻结，不加补丁**。模块 Hook 面已收敛至 READY 后零 framework Hook（账本证实），删减 Hook 不改变环境信号的存在性，"靠删 Hook 降低检测面"在探针门不可翻转的结论下进一步失去对象。

## 6. 关键修正表（早期结论 → 最终结论）

研究过程中以下早期结论被后续 E3 证据推翻或修正；本目录各报告均按修正后口径表述：

| 早期结论 | 修正后结论 | 证据 |
|---|---|---|
| "JNI 命令分发器含索引式写入 → 私有通道可远程翻转探针门" | 分发器全量反汇编 0 处索引式写入；探针门构造后**库内不可写** | 分发器 1673 条指令复核 + 写门扫描 0 命中 + 配置应用白名单核对 |
| "服务端 rollout 翻转 NetHT 探针门"是根因第一位 | 该假设排除（本库内）；服务端策略假设保留但改为"对既有信号打分/调度" | 同上 |
| sub_2A658 = 配置更新器 | 实为 **black_module 周期扫描器**（非常规路径 APK 检测），不写任何配置 | 反编译 + 写集合核对 |
| "gt" 是疑似远程开关 | gt = getToken 调用计数（首次为 1）；与恒 0 且不可写的 cfg[788] 联合决定全量快照 → **全量模式结构性不可能** | getToken worker 反汇编 |
| "每次冷启动 NetHT 初始化、nuid 常驻上行" | NetHT **懒加载/条件加载**：普通浏览会话（含登录态实测）全程不加载，请求头无 nuid | 进程 maps 全程观测（E3） |
| "设备疑似未登录态" | 设备实际**已登录**（UI 实证）；登录态真实浏览后 NetHT 仍零加载，"登录触发"假设排除 | UI 截图 + maps/logcat 阴性 |
